# FP-05 计划：五候选缓存 + 廉价样本外策略评估

> 本文件是提交给用户批准、并交由 ChatGPT Pro 审核的 FP-05 实现计划（对应本仓库
> Claude Code 会话中批准的计划）。执行 FP-00~FP-04 的完整过程记录见本目录下各
> `run_*` 子目录；本文件只是 FP-05 阶段尚未开始实现前的设计文档。

## Context

FP-03 已认证一个静态参考 adapter（Fs，`FS_SELECTED`），FP-04 已在其上认证一个 K=4/rank=4 动态专家库（`BANK_CERTIFIED`）——但两者都只证明了"机制正确、无害"，从未验证过任何样本外的真实价值。FP-05 是整个项目第一次真正回答"动态编辑到底有没有用"这个核心问题的阶段：构建 5 候选（no-edit/Fs + 4 个单专家）缓存、做跨时间的纯净样本外（purged OOF）评估、和静态 Fs 基线对比。

## 已核实的关键代码现状

- **不存在真正的数据角色隔离机制**：`earthdelta/pilot_contract.py` 里 `DataRole` 的文档已经明确写"admission 层只打标签，下游消费者自己负责校验"——直接读代码确认属实。目前没有任何代码会检查一个新准入是否和已经被 Fs/bank 训练"曝光"过的时间窗口重叠。FP-05 必须自己补上这道闸门，否则 policy_dev 数据可能和已经训练过的数据重叠，评估失真。
- **`scripts/r4_value_pilot.py` / `earthdelta/value_pilot.py` 是另一个独立"shared-F0"研究支线的代码**（文档字符串明确写"shared-F0 research pilot"），参考对象是未编辑的 F0 而不是 Fs，schema、角色数量、时间窗口全部硬编码给那条支线用，且从未在真实数据上跑过 cache/merge。**不能直接复用它的 pipeline 脚本**，只能挑其中真正通用的小工具函数（`canonical_digest`、`file_digest`、`write_json`、`assert_disjoint_roles`、`legal_features` 等）。
- FP-04 认证时 pin 住的 17 个核心源码文件全部原样未变，FP-05 的新代码必须只加新文件，不碰这 17 个文件。

## 六个已确认接受的判断

1. **policy_dev 窗口 = 2019 下半年，confirm 预留 = 2020 下半年**。理由：完全遵守已登记的 Fs/bank 曝光窗口（2020 上半年 + 2019 上半年）不需要额外的逐条净化；2020 本来就是项目的 test split 和 Stormer 自己的测试年，作为 confirm 预留更干净；dev 和 confirm 季节对齐，方便未来比较。
2. **delta_min（最小有用效应）= 0.34%**，取自 Fs 自己在 2019 留出集上实测的样本外伤害幅度（不是凭空定的数字，也不是借用 shared-F0 sprint 那次的 0.1%/0.5%）——逻辑是"动态层至少要能补回 Fs 自己造成的伤害，才算真的有用"。
3. **加一条仅报告用的 F0（原始骨干）背景轨迹**，不作为候选、不参与 oracle，只多花约 20% GPU——否则没法区分"专家库真的更好"和"专家库只是部分抵消了 Fs 自己的伤害"。
4. **一次性定样本量（预计 N=128），不做 64→128 分阶段**——避免"看了中间结果再决定要不要继续跑"这种统计上会虚高显著性的做法；到预算上限如果结果跨越阈值就诚实报告 INCONCLUSIVE，不再追加。
5. **主策略是 ridge_direct_gain，regime 分组法作为次要/描述性对照**——匹配原计划的重点。
6. **用双向阻塞交叉验证（blocked cross-fit）+ 支持窗口重叠净化，不用单向 forward-chaining**——每条数据都能拿到恰好一次样本外预测，数据本就不多（约 25 个区块），不能浪费在只做前向验证上。

## 实现方案

### Phase A（CPU）：曝光台账、数据隔离闸门、policy_dev 准入

新建 `earthdelta/split_freeze.py`：记录已曝光窗口（2020-01-01T12Z~07-04T18Z 的 Fs/bank 训练窗口，2019-01-01T12Z~07-04T18Z 的 Fs 留出窗口）、`W_dev`（2019 下半年）、`R_confirm`（2020 下半年，本阶段只预留不读取）；任何一条数据的完整支持窗口（含 t-12h 历史到 t+72h 目标）只要触碰曝光窗口两侧各加 24 小时缓冲、或触碰 confirm 预留区，一律拒绝准入。这个闸门要接入真实入口（准入脚本本身 + 缓存作业启动前 + 合并阶段 + 打分阶段），不是只在文档里写一句。

先做纯完整性扫描（只看数据有没有缺失，不看任何模型输出），冻结一份"选点声明"（时间戳早于任何数值读取），128 个均匀分布的候选时间点，缺失就近替换（规则和 FP-03/04 一致：只按数据完整性挑，不按效果挑）。然后走真实 `r2_admission_gate.py --data-role policy_dev --verify-content` 拿到内容认证。8 个调试用 issue 直接从 FP-04 已经训练过的数据里各组挑首尾各一条（反正已经曝光过，用来验证机制而非产生新信息）。

### Phase B（CPU）：新代码 + 测试

新增 `earthdelta/candidate_cache.py`（复用 FP-04 已建立的证书加载/校验模式，绑定到认证 Fs + 认证 bank，而不是 shared-F0 的 schema）、`earthdelta/policy_oof.py`（分区/折/净化、numpy 实现的 scaler/PCA/ridge/k-means、预测冻结、打分器、配对区块自助法）、`scripts/r4_candidate_cache.py`、`scripts/r4_cache_decide.py`、`scripts/r4_policy_oof.py`，以及对应新测试（`tests/test_split_freeze.py`、`tests/test_plan_cache_evaluation.py`）。关键测试要覆盖：越界窗口被拒绝；矩阵完整性/身份/字节校验；特征构造不依赖任何真值（扰动真值不改变特征哈希）；用毒化的验证折标签重跑 fit，输出必须逐位不变（证明真的没读到验证标签）；净化后训练/验证窗口互不重叠；打分器没有冻结文件就拒绝运行。

### Phase C（CPU）：预注册协议冻结

新协议文件绑定：认证 Fs 的完整引用、认证 bank 的 registry、S0 证书、FP-04 协议哈希、split_freeze 台账、policy_dev/调试准入、FP-04 pin 住的 17 个核心文件哈希（必须逐一核对未变）。协议里包含：per-worker 有效性校验规则、逐候选逐 issue 逐时效的产出格式和精确校验规则（覆盖率/身份/字节/CPU 独立重算校验 GPU 结果/解析梯度校验）、调试批次通过标准（含"调试 issue 的 Fs/专家损失必须和 FP-04 已有记录逐位相等"这条硬锚点）、按真实吞吐/存储/显存预算机械选定开发规模的规则（不按结果好坏选）、交叉验证的分折与净化规则、五种候选选择方法（no-edit、fold-train 最优静态、区域路由、ridge 直接收益预测、hindsight oracle 仅用于诊断）、delta_min 判定规则、以及供 FP-06 直接套用的判决顺序（跨越阈值一律 INCONCLUSIVE，不自行放宽）。

### GPU 作业与预算（预计 2 个，上限 4 个）

- **C-J1 调试批**：4 个 worker，含交叉重复校验（每条数据被两个 worker 各算一次，输出必须逐位相等），且必须和 FP-04 已有的逐 issue 损失记录精确对上。
- **C-J2 正式缓存**：4 分片，只有调试批完全通过、开发规模按机械规则定好之后才提交。
- 1 次基础设施重试额度；任何校验失败（非基础设施原因）直接判定证据无效，不自动放宽。

之后的策略拟合、打分、统计推断全部是 CPU 工作，不消耗 GPU 预算。

## 验证方式（每个节点，父会话独立复核）

- 协议冻结前：独立重算 17 个 pin 文件哈希、独立重建曝光窗口列表、独立核对每条 policy_dev 数据的支持窗口确实不碰任何曝光/预留区。
- 调试批之后：把调试损失和 FP-04 已有的 `bank_panels_expert{k}.json` 逐个数字比对（不只是信任判定文件）。
- 正式缓存合并之后（**不看任何损失数值**）：核对覆盖率、身份、文件哈希，确认日志里没有泄漏任何损失值，确认只读取了认证窗口内的存储索引。
- 策略拟合之后：独立重算净化逻辑确认无重叠；用验证标签毒化后重跑，确认预测文件逐位不变。
- 打分之后：独立用 numpy 重算最终效应表和置信区间，核对没有任何 confirm 窗口被访问过。

## 本阶段不做的事

FP-06 最终决策本身（FP-05 只负责冻结规则、产出 ABOVE/BELOW/STRADDLE 判定，不下结论）；dual-head/E3/JEPA/memory 等；打开或读取 confirm（只做预留声明）；重新训练或重新选择 Fs/专家、改变 K；任何看到结果后扩大样本量的行为；拉取 2021 数据；修改 FP-04 pin 住的任何文件。

## 需要提前说明的风险

- **空结果（专家库不比 Fs 好）是完全可能、且必须被诚实报告的结果**——Fs 自己在样本外的收益已经归零，专家只在训练组内部改善过，季节还不匹配（训练在 1-6 月、评估在 7-12 月），这些都指向"可能测不出真实收益"。
- Oracle（事后最优选择）机械上几乎总是正的，它的价值在于和 delta_min 比较置信区间，不在于符号本身。
- 数据可用性可能限制不到 128 的样本量，样本量不足时 INCONCLUSIVE 是合法的最终结论，不代表方法本身失败。
